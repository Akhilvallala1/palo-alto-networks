# Conduit Security

Conduit sits between application code and model vendors, so it inherits three
jobs: keep sensitive data out of a vendor's logs, keep adversarial input from
steering a model, and keep credentials out of everything — the repository, the
image, the CI log, and the container's environment.

This document states what is enforced, what is measured, and where the measured
number falls short of the target. A security document that only lists controls
is a brochure.

---

## Threat model

**In scope.**

| Threat | Control | Where |
|---|---|---|
| PII reaching a vendor | reversible redaction before the provider call | `guards/pii.py` |
| Placeholders reaching the caller | rehydration from the ingress entity map | `gateway/pipeline.py` |
| Prompt injection / instruction override | layered detector, fail-closed above threshold | `guards/injection.py` |
| An unknown caller | static API key → team, quota, ceiling | `gateway/auth.py` |
| One caller starving the rest | per-key token bucket | `gateway/ratelimit.py` |
| Runaway spend | per-key daily ledger, downgrade or 429 | `router/cost.py` |
| Vendor lock-in / silent SDK creep | AST guard over every module | `tests/test_no_vendor_imports.py` |
| Credential in a build log | Secret Manager references, never values | `.github/workflows/deploy.yml` |
| Container escape blast radius | non-root uid 10001, no shell, core-only install | `infra/Dockerfile` |

**Out of scope**, deliberately, and named in the epic: SSO/OIDC (static API keys,
exactly like the `mcp-gateway` prior art), multi-tenant data isolation beyond
per-key accounting, model fine-tuning, and any integration with real customer
data. The GTM corpus is synthetic and generated by `scripts/seed_gtm_data.py`.

## The pipeline's structural guarantees

Order is enforced, not documented. `gateway/pipeline.py` holds a `StageLog`
that rejects any stage which does not come strictly after the last one:

```
auth → ingress_guard → router → provider → egress_guard → telemetry
```

Two consequences worth stating explicitly:

- **Auth is a FastAPI dependency, not middleware.** A route body cannot run
  before its dependencies resolve, so an unauthenticated request cannot reach a
  guard, a router, or a provider no matter what a handler does.
- **The guard runs before the router.** Reordering them — to classify complexity
  on the raw prompt, say — would send unredacted text to the tie-break model.
  That reordering raises `PipelineOrderError` at runtime instead of shipping.

### Redaction round-trips

The vendor payload contains zero raw PII; the caller's response contains zero
placeholders. Both directions are asserted by test, not by inspection
(`tests/test_guards_roundtrip.py`).

The subtle part is that redaction is **per-request, not per-message**.
`GuardChain` restarts its `<PERSON_n>` counters on each call, so inspecting each
message separately would mint two different `<PERSON_1>`s and merge them into one
entity map — rehydrating the wrong name into the caller's answer. The chain
therefore sees the whole prompt joined, and the map is applied back per message.

The egress guard **observes and does not redact**. Applying its `redacted_text`
would hand the caller fresh placeholders that the ingress map cannot resolve,
which is exactly what the round-trip criterion forbids.

### Fail-closed, and what that costs

`config/guards.yaml` ships `fail_closed: true` with an injection risk threshold
of `0.7` and a PII score threshold of `0.5`. A verdict at or above threshold
blocks the request with HTTP 400 and a logged verdict carrying category and
score. Every verdict is logged, blocked or not.

### A fabricated answer is a security failure, not a fallback (issue #14)

Every chain in `config/routing.yaml` ends in `mock:echo` so a zero-key checkout
still serves. Left unqualified that is a liability: a deployment holding a real
credential, during a vendor outage, would walk the chain to that last hop and
return invented text as HTTP 200 with `cost_usd: 0.0`. Nothing downstream — not
the L2C workflow, not the caller, not the telemetry row — can distinguish it
from a real completion. Silent wrong answers are worse than loud failure,
especially on a path that quotes prices.

`mock` is therefore dormant whenever any provider credential is present. An
exhausted chain raises `AllProvidersFailedError` and the request fails. The
override, `CONDUIT_ALLOW_MOCK=1`, exists for tests and demos, and logs a warning
naming the credentialed providers whenever it is what kept mock reachable.

This is enforced in `available_providers` rather than in config, because a
config-only rule is one careless `routing.yaml` edit from being untrue.

## Measured, including where it falls short

Two corpora, measured two ways. `tests/fixtures/*.jsonl` are the gating
fixtures the suite asserts against; `evals/golden/guards.jsonl` was authored
under issue #8 from the attack descriptions in `docs/SPEC.md`, never from
`guards/injection.py`'s patterns.

| Criterion | Target | Measured | Status |
|---|---|---|---|
| PII recall (`pii_corpus.jsonl`, gated by test) | ≥95% | ≥95%, per entity type too | met |
| PII false positives | ≤5% | ≤5% | met |
| PII on the independent slice | — | 9/10 | see below |
| Injection detection (independent slice) | ≥90% | **70.0%** (21/30) | **unmet** |
| Injection false positives on benign lookalikes | ≤10% | **0.0%** of 20 | met |

The injection number is stated rather than tuned away, and the miss profile is
what makes it actionable. The split is clean with nothing in between: every
`instruction_override` case scores 0.94–1.00 and is caught, as is every
`obfuscation` case. What is missed is attacks phrased as ordinary business
requests — `role_switch` (3 of 4 missed), `prompt_exfil` (2 of 4), `tool_abuse`
(2 of 3). Those score 0.07–0.35, nowhere near the 0.7 block threshold, so this
is a coverage gap in the pattern set and **not** a threshold that needs nudging;
lowering the threshold would cost false positives without catching them. Closing
it properly means the optional LLM classifier
(`injection.llm_classifier`), which is off by default because it adds a model
call to every high-risk request.

The one PII miss on the independent slice is a bare person name with no
co-occurring identifier. Presidio is an optional dependency and is not installed
in the measured environment, so the regex analyzer — which has no pattern for
names — sees nothing. A dependency gap rather than a logic bug, but a real hole
in the configuration that was actually measured, and scored as a failure rather
than excused.

Treat the injection guard as defence in depth, not as a boundary you can lean on
alone.

## Secret handling

### The repository holds no secret

`.gitignore` excludes `.env` and `.env.*`; `.dockerignore` excludes them again,
so a stray `.env` on a developer's machine cannot be copied into an image by a
wide build context. `config/gateway.yaml` contains demo API keys — `conduit-demo-key`
and `conduit-trivial-key` — which are *credentials for a local mock stack*, not
secrets. Override them in any real deployment:

```bash
CONDUIT_GATEWAY__API_KEYS='[{"key":"...","team":"gtm","max_tier":"complex"}]'
```

### CI holds no secret

`.github/workflows/ci.yml` reads no secret, sets no API key, and declares
`permissions: contents: read`. This is not tidiness: the registry only
instantiates an adapter whose key env var is present, so an unset key is what
makes CI exercise the same mock + Ollama path a clean machine gets. rival-radar's
CI sets `ANTHROPIC_API_KEY: test-key` to get past import time; Conduit does not
need to, and setting one would quietly test a configuration nobody ships.

### Deploy passes references, never values

Three properties, each chosen against a specific way secrets leak:

1. **Workload Identity Federation, not a JSON key.** GitHub mints a short-lived
   OIDC token that GCP exchanges for credentials. There is no long-lived service
   account key stored in the repository, so there is nothing to print.
2. **`--set-secrets`, not `--set-env-vars`.** Cloud Run receives Secret Manager
   *resource names* (`conduit-anthropic-api-key:latest`) and resolves them inside
   GCP at container start. The value never enters the runner's memory, let alone
   its log. The prior-art workflow used
   `--set-env-vars "ANTHROPIC_API_KEY=${{ secrets.… }}"`, which materialises the
   value into a command line — the one thing this workflow must not do.
3. **No step echoes anything sensitive.** The identity token used by the
   post-deploy smoke test is produced and consumed inside a single `curl`
   argument by command substitution; it is never assigned to a shell variable,
   exported, or printed.

The deploy workflow is `workflow_dispatch`-only. There is no `push` trigger, no
`release` trigger, and no `workflow_run: [CI]` chain. Shipping is a decision
someone makes behind a GitHub environment approval, not a side effect of merging.

### One-time GCP setup

```bash
PROJECT_ID=your-project
REGION=us-central1

# 1. Artifact Registry for the image
gcloud artifacts repositories create conduit \
  --repository-format=docker --location="$REGION"

# 2. The secrets Cloud Run will resolve. Values are piped, never passed as
#    arguments, so they do not land in your shell history.
printf '%s' "$ANTHROPIC_KEY" | gcloud secrets create conduit-anthropic-api-key --data-file=-
printf '%s' "$GATEWAY_KEYS_JSON" | gcloud secrets create conduit-gateway-api-keys --data-file=-

# 3. The runtime service account may read those secrets, and nothing else.
gcloud secrets add-iam-policy-binding conduit-anthropic-api-key \
  --member="serviceAccount:$RUNTIME_SA" --role=roles/secretmanager.secretAccessor

# 4. Workload Identity Federation, scoped to this repository alone.
gcloud iam workload-identity-pools create github --location=global
gcloud iam workload-identity-pools providers create-oidc github-actions \
  --location=global --workload-identity-pool=github \
  --issuer-uri=https://token.actions.githubusercontent.com \
  --attribute-mapping='google.subject=assertion.sub,attribute.repository=assertion.repository' \
  --attribute-condition='assertion.repository == "Akhilvallala1/palo-alto-networks"'
```

Then set the repository secrets `GCP_PROJECT_ID`, `GCP_WIF_PROVIDER`,
`GCP_DEPLOY_SERVICE_ACCOUNT`, `GCP_RUNTIME_SERVICE_ACCOUNT`. The attribute
condition in step 4 is what stops another repository from borrowing the pool.

## Container hardening

| Property | How | Verify |
|---|---|---|
| Non-root | `USER 10001:10001`, pinned uid/gid | `docker compose exec gateway id` |
| No login shell for that user | `useradd --shell /usr/sbin/nologin` | — |
| No build toolchain in the runtime | multi-stage; only `/opt/venv` crosses | `docker history` |
| No vendor SDK in the image | core distribution only, no extras installed | `pip list` in the container |
| Healthcheck without extra packages | `python -c urllib.request…`, no curl added | `docker inspect …Health.Status` |
| No credential in the container | compose declares none; keys arrive via optional `.env` | `docker compose exec gateway env` |

The last row is the compose-level form of the zero-key claim and is asserted by
`tests/test_compose_e2e.py::test_no_service_is_handed_a_vendor_credential`, plus
a CI step that greps the running container's environment and fails on a match.

## Data retention

`config/telemetry.yaml` ships `persist_text: false`. Turning it on persists raw
prompt and completion text next to the cost rows, where it outlives the request
and lands in a file nobody scrubs. It is a config value rather than a
constructor default precisely so that flipping it is a visible, reviewable
decision. Leave it off outside a local debugging session.

Telemetry otherwise stores metadata only: model, provider, tier, token counts,
cost, latency, guard verdict categories, and a trace id.
